> 场景：在**现有项目继续运行**的前提下，在**同一台 2GB 服务器**上加第三个应用，
> 并把**主域名首屏**交给它。
>
> 本文只做设计，不含实现。所有端口、内存、路径都以当前服务器实测状态为基准。

## 1. 端口规划（重点）

### 1.1 分配原则

1. **公网只开 80 / 443**，其余全部绑定 `127.0.0.1`
2. **一个应用 = 一个端口**：HTTP 与 WebSocket **用同一个端口**，不要为 WS 单开
   （uvicorn 原生在同一端口同时处理 HTTP 与 WS）
3. **`180xx` 段** 专用于「绑在 127.0.0.1 的应用后端」，顺序递增
4. **加新应用前先查占用**：
   ```bash
   sudo ss -tulpn | grep -E ':(80|443|5000|8080|15568|180[0-9][0-9])\b'
   ```
5. **compose 里必须写 `127.0.0.1:端口:容器端口`**，不能写 `端口:容器端口`
   —— 后者绑定 `0.0.0.0`，等于把服务直接暴露到公网
   （点餐系统当初就是这个问题）

### 1.2 端口分配表

| 端口 | 绑定 | 用途 | 状态 |
|---|---|---|---|
| 22 | `0.0.0.0` | SSH | 已有 |
| 80 | `0.0.0.0` | nginx：HTTP → HTTPS 跳转 | 已有 |
| 443 | `0.0.0.0` | **nginx：全机唯一公网入口** | 已有 |
| 5000 | `127.0.0.1` | tsx-app（点餐系统） | 待收紧 |
| 8080 | `127.0.0.1` | searxng | 已有 |
| 15568 | `127.0.0.1` | OpenClaw 网关 | 已有 |
| 18001 | `127.0.0.1` | easkb-app（售后 Agent） | 已有 |
| **18002** | **`127.0.0.1`** | **resume-bot 后端（HTTP + WS 同端口）** | **本次新增** |

**未来扩展**：下一个应用用 `18003`，依此类推。若某应用要拆成前端 + 后端两个容器，
则前端用 `181xx` 段、后端用 `180xx` 段，避免混在一起。

> 不建议用 `3000/8000` 这类常见端口：一是容易和别的项目撞，
> 二是这些端口常被扫描器盯上，绑到 `0.0.0.0` 时风险更高。

### 1.3 nginx 侧要开的三条路径

主域名（`<主域名>`）的 server 块需要三处改动：

```nginx
server {
    listen 443 ssl;
    server_name <主域名>;

    ssl_certificate     /etc/letsencrypt/live/<主域名>/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/<主域名>/privkey.pem;

    # ① 前端静态资源（resume-bot 构建产物）
    root /opt/apps/resume-bot/frontend/dist;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }

    # ② 普通 API
    location /api/ {
        proxy_pass http://127.0.0.1:18002/;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # ③ WebSocket —— 这一段最容易漏，漏了会 400/426
    location /ws {
        proxy_pass http://127.0.0.1:18002;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host       $host;
        proxy_read_timeout 3600s;      # WS 是长连接，别用默认 60s
        proxy_send_timeout 3600s;
    }
}
```

> **证书不用新申请**：现有证书已覆盖 `<主域名>` 与 `www.<主域名>`，
> 所以首屏换内容**不需要新的子域名、也不需要新证书**。这是把首屏放在主域名的一个实际好处。

### 瘦身要点（照着做，否则很容易吃 400 MiB）

| 做法 | 省下 |
|---|---|
| **不要引入向量库**（Chroma / FAISS） | 约 250 MiB |
| **不要引入 MySQL / Redis 容器** | 约 480 MiB |
| 用 SQLite（WAL 模式）+ 内存事实库 | — |
| uvicorn **单 worker** | 每多一个 worker 多一份完整进程 |
| 不装 `numpy` / `pandas` 这类重依赖 | 约 50 MiB |
| 镜像基于 `python:3.12-slim`，只装必要依赖 | — |

> **为什么不需要向量库**：简历语料只有几千字。
> RAG 在这里是**过度设计**——它会引入检索失败、增加内存、还多一个故障点。
> 正确做法见 §4.2。

## 4. 代码注意事项

### 4.1 复用而不是重造

| 已有能力 | 怎么复用 |
|---|---|
| 确定性意图路由 | 沿用售后项目的「关键词优先 + 兜底分类」设计，保持架构一致 |
| 飞书出站通知 | 复制 `feishu_client` 的思路（**复制代码而不是跨项目 import**，避免耦合） |
| 审计日志模式 | 沿用「谁 / 何时 / 做了什么 / 结果」的结构化写法 |
| 管理后台鉴权 | 沿用 JWT + 权限点，管理员端必须登录 |
| Dockerfile / compose 写法 | 沿用售后项目的生产实践（非 root、单 worker、日志轮转、内存上限） |

> **但不要为了"统一"而强行统一**：简历机器人流程简单（接待 → 对话 → 转人工 → 结束），
> 用**线性状态机 + 确定性路由**就够，不需要 LangGraph。
> 面试时这反而是加分项——**能说明"为什么两个项目选型不同"比"两个都上 LangGraph"更能体现判断力**。

### 4.2 防幻觉（这是这个项目的核心卖点）

**事实库设计**

- 用 YAML/JSON，每个事实一条，**稳定 ID**（`F-001`…）
- 按主题分组：基本信息 / 技能 / 项目 / 经历 / 可公开的联系方式
- **事实库里没有的内容，系统一律不回答**（不靠模型"想当然"）

**检索策略：不做 RAG，全量注入**

简历语料只有几千字，直接整份放进 system prompt：

| 方案 | 准确率 | 内存 | 故障点 |
|---|---|---|---|
| 向量 RAG | 中（可能检索不到） | +250 MiB | 检索失败、索引损坏 |
| **全量注入 + 引用 ID** | **高** | **~0** | 无 |

**确定性验证器（关键）**

模型输出后、返回给用户前，跑一遍校验：

1. 回答里引用的 `F-0xx` 必须**真实存在**于事实库
2. 回答里出现的**数字、公司名、时间、链接**必须能在事实库找到出处
3. 任一不满足 → **不放行**：要么让模型重写一次，要么降级为"这个我不确定，可以转本人确认"

**证据锚点**

- 每个技术论断必须挂事实 ID + GitHub 链接
- 链接**来自事实库**，不允许模型自己拼 URL（防幻觉链接）

### 4.3 WebSocket 与背压

| 注意点 | 做法 |
|---|---|
| **必须单 worker** | WS 是有状态的。多 worker 会导致同一会话被路由到不同进程、互相看不到连接。要扩就得引入 Redis pub/sub，得不偿失 |
| **有界队列** | `asyncio.Queue(maxsize=N)`，防止慢客户端把内存撑爆 |
| **队列满的策略** | 不要无限等。建议：达到 80% 时**降级为非流式**（发整段）；满了则**丢弃增量 token、只保留最终消息**，并告知前端 |
| **心跳** | 定期 ping/pong + 空闲超时清理，防僵尸连接 |
| **连接数上限** | 全局与会话双上限，超了拒绝新连接而不是拖垮服务 |
| **打断** | 用户可能在 AI 说话时插话 → 必须能 `task.cancel()` 取消正在生成的请求 |
| **nginx 配置** | 见 §1.3 的 ③，`Upgrade` + `Connection` + 长 `proxy_read_timeout` 一个都不能少 |

### 4.4 落库策略

| 注意点 | 做法 |
|---|---|
| **不要逐 token 写库** | IO 会爆炸。用户消息立即落；AI 消息**流结束后落一次** |
| SQLite 开 WAL | 提升并发读性能 |
| 独立 DB 文件 | 与售后项目分开（各自 `data/`），互不影响 |
| 表设计 | 会话 / 消息 / 事件 / 提醒 分表，事件要结构化（页面、控件、时间） |
| 挂卷 | `./data:/app/data`，容器重建不丢 |

### 4.5 安全（面试官会重点看这块）

| 风险 | 对策 |
|---|---|
| **XSS** | Markdown 渲染**必须消毒**（DOMPurify）。AI 输出属于不可信内容，绝不能直接 `v-html` |
| **Prompt 注入** | 访客可以输入"忽略以上指令"。事实库与系统提示要隔离；工具调用走白名单；输出仍过验证器 |
| **API 被刷爆** | 匿名访客能调 LLM → **必做**每 IP / 每会话的速率限制 + 单会话 token 上限 + 全局日预算上限。这是最现实的账单风险 |
| **iframe 通信** | 收发 `postMessage` **双向校验 `event.origin`**，白名单精确匹配，不用 `*` |
| **点击劫持** | 主域名允许被自己嵌入（`frame-ancestors` 只放开需要的来源） |
| **管理员端** | 必须登录；**接管操作要写审计**；接管期间 AI 必须真的静默（后端状态机保证，不能只靠前端隐藏） |
| **个人信息** | 简历里的手机号/邮箱对外要收敛——放"请求联系方式"按钮，而不是明文列出 |

### 4.6 iframe 嵌入 Demo 的两个实际问题

**问题一：售后 Agent 需要登录** ⚠️

面试官点开 Demo 会直接撞到登录页，体验很差。三种解法：

| 方案 | 评价 |
|---|---|
| **只读演示账号，凭据写在卡片上**（推荐） | 简单、安全、可控。售后项目已有 21 个权限点，建一个只读角色即可 |
| 带签名的自动登录链接 | 体验最好，但等于开了一个鉴权后门，要非常小心（短时效 + 单次 + 只读） |
| 单独做一个"演示模式"路由 | 工作量最大 |

**问题二：跨域 iframe 的存储**

- 两个站点不同源，`localStorage` 各自独立 ✓ 互不干扰
- 如果将来改用 **Cookie** 存 token，要注意第三方 iframe 下 `SameSite=Lax` 的 Cookie **不会发送**
  —— 当前用 `localStorage` 所以没这个问题，但换方案时要记得

**问题三：悬浮导览机器人**

原方案依赖子页面 `postMessage` 上报点击（如"我是店长"）。这需要**改动两个现有项目**，
有回归风险。建议分两期：

| 期 | 做法 | 侵入性 |
|---|---|---|
| **一期** | 悬浮机器人在**父页面**，由父页面的工具栏按钮驱动（"我是店长 / 看后台 / 看技术栈"） | 零侵入 |
| **二期** | 给子项目加**轻量埋点**（一个 `postMessage` helper + feature flag，默认关闭） | 低，且可开关 |

一期就足够展示"悬浮导览"这个亮点，二期再补真实交互。

### 4.7 体验细节（容易被忽略但很影响观感）

| 细节 | 做法 |
|---|---|
| **首屏不等待** | 主动接待那句话说**预置文案**，不要等 LLM 生成（否则首屏空 2–3 秒） |
| **移动端** | 面试官很可能用手机点开，响应式必须做 |
| **降级** | LLM 挂了要有兜底：展示静态介绍 + 联系方式，不能让访客看到报错堆栈 |
| **静态资源** | 全部由 nginx 直接托管，不要经过后端 |
| **转人工提示** | 切换时要插入明确提示（"已转由本人回复"），否则访客会以为 AI 卡了 |

### 4.8 转人工的通道选择

| 通道 | 评价 |
|---|---|
| **飞书**（推荐） | 已有可用应用与出站能力，直接复用 |
| **企业微信** | 可行，但需要单独配置应用与凭据 |
| **个人微信** | ❌ **不建议**：没有官方接口，靠非官方方案违反服务条款且有封号风险 |

**分级提醒建议**：

| 级别 | 触发 | 通道 |
|---|---|---|
| 普通 | 访客主动要求转人工 | 飞书私聊 |
| **紧急** | 识别到「合作 / 面试 / 薪资 / 招聘」等高价值意图 | 飞书 + **电话或短信**（比微信可靠） |

> 时间敏感的场景，微信不是好选择——它没有可靠的服务端推送保证。

## 5. 分期落地建议

| 期 | 目标 | 产出 |
|---|---|---|
| **一期（核心可用）** | 首屏接待 + 流式对话 + 事实库 + 验证器 + 证据锚点 + 转人工飞书提醒 | 面试官能完整对话并看到可信回答 |
| **二期（导览）** | 项目卡片 + iframe Demo（含只读演示账号）+ 悬浮导览（父页面驱动） | 能"点进去看真实系统" |
| **三期（管理端）** | 会话监控 + 一键接管 + 落库 + 常见问题统计 | 你能实时接住面试官 |
| **四期（打磨）** | 响应式、降级、限流、埋点（子项目） | 对外可放心公开 |

**建议按这个顺序**：一期不做完就不要碰二期。因为"AI 能可靠回答技术追问"是这个项目的灵魂，
导览和管理端都是加分项，不是必需品。
